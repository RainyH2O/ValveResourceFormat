## Project Overview

ValveResourceFormat (VRF) is a C# library and toolset for parsing Valve's Source 2 resource formats. Solution: `ValveResourceFormat.slnx`. Targets the latest released .NET with nullable reference types enabled. CI builds Release, which enables `TreatWarningsAsErrors` and all analyzers.

- **ValveResourceFormat/**: Core parsing library published to NuGet
- **GUI/**: WinForms viewer
    - `Source2Viewer.exe --mcp` serves an HTTP MCP server at `http://127.0.0.1:13338/mcp`, letting an agent open files, drive the camera and sidebar controls, inspect entities, models and particle systems, pick, trace, pause and step simulation time, read the log and render stats, and screenshot the real viewer. `--mcp=<port>` serves on another port, to run several viewers at once. Debug builds only; the tools are `[Tool]` methods of `McpTools` in `GUI/Automation/`.
- **CLI/**: Command-line decompiler and file viewer, usage in `docs/guides/command-line.md`
- **Renderer/**: OpenGL renderer
    - Shaders are GLSL in `.slang` files (`.frag.slang`, `.vert.slang`) and must be ASCII only.
    - After changing shaders, run `dotnet run --project Misc/ShaderValidator -- <name filter>` to compile all their combos on a real GL context. `complex` is too slow for this, so iterate on a smaller shader.
    - `Renderer/Editor/` is the editor like layer on top of the renderer: selection, picking, tools visibility, and the Hammer stand-ins and lines drawn for entities. The rest of the renderer only draws what the game shows and leaves tool visuals to the `IEntityToolVisuals` hook.
- **Tests/**: TUnit suite for the library, plus headless Renderer logic tests in `Tests/Renderer/`. GUI and CLI are not covered.
    - Run the full suite with `dotnet test` when changing `ValveResourceFormat/` or `Renderer/`. On `Zero tests ran` (exit code 5), do a full `dotnet build` and retry.
    - When a parsing change legitimately alters text output, `VRF_REGEN_FIXTURES=1` rewrites the mismatching `Tests/Files/ValidOutput` dumps.
    - Download workshop items and game files to test with, including old builds and single VPK entries, with [SteamFileDownloader](https://github.com/SteamTracking/SteamFileDownloader).
- **Misc/**: Auxiliary tools (ShaderValidator, RenderTest, etc.) in their own solution `Misc/MiscVrfProjects.slnx`.
- **docs/**: VitePress site. When changing what VRF can parse, decompile, or export, update the support matrix and limitation tables in `docs/guides/format-support.md` in the same change.

### Building

- Release is slow, so iterate in Debug, run `dotnet build <changed project> -c Release --no-restore` in the background, and fix its warnings before finishing.
- When a change uses reflection, `Type.GetType`, `Activator`, `MakeGenericType`, non-generic `Enum` APIs or serialization, add `-p:CheckAot=true` to the Release build.
- Fix formatting with `dotnet format whitespace --include <changed files>`.

### Adding Formats

- New code goes in the library first, GUI and CLI consume it. New formats should at least print parsed info in the CLI.
- New formats or versions need the smallest possible sample in `Tests/Files`. Non-`_c` files also need an explicit test that loads them.

### Manually Maintained Mappings

- `EntityLumpKnownKeys.cs`: entity key names for hash lookup, sorted ignoring case. Collect unknown hashes with CLI `--test --test_entity_keys` and resolve them with `Misc/MurmurHashMatcher`.
- `ValveResourceFormat/IO/Fgd/entity_classes.kv3`: generated by `Misc/VrfFgdParser` from the FGD files of installed games, one table per Steam app id, don't hand-edit. Tables of games not installed are kept.
- `ValveResourceFormat/IO/Fgd/entity_classes_extra.kv3`: kept by hand for classes no FGD file declares, used with the merged table of games whose classes are not known.
- `MapExtract.cs`: entity and collision tags mapped to Hammer tool textures.
- `ShaderDataProvider.cs`: per-shader texture and channel fallbacks for material extraction.
- `GUI/Icons/AssetTypes`: SVG icon per extension, with extra extensions mapped in `aliases.txt`.

### Shader Pipeline

- `GetShaderFileByName()` maps each `.vfx` name to one of our shaders (e.g. `csgo_environment_blend.vfx` -> `csgo_environment`), falling back to `complex`.
- At compile time, `GameVfx_{vfxName}` (e.g. `GameVfx_vr_complex`) is defined as 1 to enable shader-specific `#if` paths; all other `GameVfx_` defines are 0.

### Transforms and Angles

All angle, quaternion and direction conversions live in `EntityTransformHelper`. Use it instead of hand-rolling trig, and read its class remarks before touching this area.

- Source 2 is Z-up and right-handed: +X forward, +Y left, +Z up.
- An entity's `angles` is a QAngle: (pitch, yaw, roll) in degrees, pitch positive **downwards**.
- Matrices are row-vector, so a rotation's first row is forward. Frames built from a direction must put it on +X.
- `Camera` holds the same angles in radians. Convert at that boundary via `Camera.SetFromQAngle`/`GetQAngle`.

## Custom Branch Features

`custom` is a long-lived feature branch based on `master`. The items below describe intentional behavior that must survive rebases and later maintenance.

When rebasing, use the latest `master` code, APIs, naming, and architecture as the implementation baseline. Reapply the required custom behavior to that baseline instead of restoring obsolete custom implementation details. Update this section whenever a custom feature is added, removed, or materially changed.

After every rebase, promptly report every problem discovered during conflict resolution, review, builds, tests, or manual verification. Explain its impact, whether it was introduced by the current rebase, an earlier rebase, or pre-existing code, and whether it was fixed or remains unresolved. If its origin is uncertain, say so. Do not omit a discovered problem because it predates the current rebase, and do not claim full completion while required behavior is known to be broken. Fix discovered regressions affecting required feature behavior as part of the rebase task when authorized and feasible; report any remaining blocker explicitly.

During Custom implementation and maintenance, minimize divergence from `master`. Prefer the smallest localized change that satisfies the required behavior, and avoid refactoring or replacing `master` architecture unless the existing structure cannot support a safe solution. When broader changes are necessary, state the reason explicitly before implementing them.

Apply the open-closed principle to Custom work: keep `master` implementations and their default behavior closed to unnecessary modification, while making Custom behavior open through new files, partial or derived types, composition, adapters, and narrowly scoped extension points. Continue to depend on and reuse `master` APIs and implementations rather than duplicating them; complete independence from `master` is not a goal. Modify an existing file when the capability belongs in that type or when a small general-purpose hook is required, but keep the Custom policy and orchestration outside it whenever practical.

During Custom work, preserve the exact formatting of files and lines inherited unchanged from `master`, including BOMs, using order, and indentation. Never run solution-wide `dotnet format` on this branch. Format only files intentionally changed for the current Custom work, using an explicit `dotnet format --include <paths>` scope, then inspect the resulting diff and discard any unrelated formatting changes.

### Entity Browsing and Navigation

- Purpose: make map entities searchable and navigable from the 3D world viewer.
- Required behavior:
  - `Ctrl+Alt+R` opens a reusable entity list for the loaded world.
  - The entity list supports property key/value filters, exact matching, comma-OR/plus-AND/exclamation-NOT expressions, outgoing I/O filters, and per-column filters. Active property and I/O filters add columns showing the matched data.
  - Entity-list columns use bounded content sizing, preserve manually adjusted widths during filtering, and sort text with numeric segments naturally. Column filters track horizontal scrolling; the property and I/O filter panel can be collapsed, and window size is remembered for the application session.
  - Selecting a row highlights the corresponding scene node; when the per-window sync checkbox is enabled, MAP selection changes select matching visible rows without changing filters; double-clicking selects it and moves the camera to it.
  - EntityList can add its selected rows to an independent fixed-highlight collection, remove selected rows from it, or clear it; pinned rows keep a tinted background and left-edge marker without an extra column, including after filtering; closing and reopening the list clears that collection while ordinary selection clearing on entering Walk mode (`X`) remains unchanged.
  - All list actions remain below the grid: a pinned-highlight count with Add/Remove/Clear, a separate filter/column-width/MAP-to-list group, and an independent Export button. Groups wrap together in narrow windows; tooltips explain synchronization direction and that clearing pinned highlights keeps ordinary selection.
  - `Ctrl+G` navigates by entity target name, world coordinate, or Hammer ID. Target-name lookup tries an exact match first, then a case-insensitive partial match, and prompts when multiple nodes match. The resizable multi-match dialog shows entity name, classname, and Hammer ID, with column-header toggles for ascending or descending natural sorting. Like the entity list, it preserves input order until a column header is clicked.
  - `Ctrl+Shift+E` moves the camera to the currently selected entity using the EntityList double-click focus behavior; with multiple selected entities, it prompts for one entity using the GoTo-style selection dialog.
  - `Alt+Enter` opens information for the selected entity or scene node.
  - The standalone EntityInfo window leaves single-click property interactions passive; double-clicking a property value tries coordinate, Hammer ID, and entity-name navigation, selecting and focusing matched entities and reusing the multiple-match dialog. Resource-reference values retain their external-open behavior.
- Main integration points: `GUI/Forms/EntityListForm.cs`, `GUI/Forms/GoToForm.cs`, `GUI/Controls/EntityInfoControl.cs`, `GUI/Controls/RendererControl.cs`, `GUI/Types/GLViewers/GLWorldViewer.cs`, `GUI/Utils/KeybindingRegistry.cs`, and selection helpers in `Renderer/`.
- Invariants: navigation must search both the main and 3D skybox scenes, MAP-to-list synchronization defaults off and is not persisted, list-to-MAP selection remains active regardless of that checkbox, fixed highlights remain independent of ordinary selection and do not enter MAP/list synchronization, deleting coordinate markers removes their fixed highlights, pinned-only light-probe debug grids are cleared when unpinned or leaving the debug mode, synchronization must not create an event loop, coordinate navigation must preserve camera-transition history, and opening a second entity-list window for the same viewer must be avoided.

### Gameplay Flow Recording

- Purpose: record, narrate, persist, and revisit focused gameplay scenes while exploring a map.
- Required behavior:
  - The world-viewer Tools controls open one reusable gameplay-flow window per world viewer.
  - A document normally belongs to one map and can contain multiple independent root flows. Any node can optionally own one child flow, allowing finite nested flows without changing the default flat workflow.
  - Each flow stores nodes in reading order with automatic hierarchical numbering, optional non-contiguous groups that can form an acyclic hierarchy, and explicit acyclic connections that support branches, merges, and disconnected paths.
  - Capturing creates a node without blocking and records the camera position, QAngle, FOV, renderable entity selection, node-owned annotation points, and viewer-shortcut visibility mask. Selecting a node restores that focused state immediately without changing other viewer visibility or rendering preferences.
  - Routine flow, node, group, and child-flow creation and deletion are immediate; new containers receive unique default names, while unsaved-change confirmation is deferred until closing or replacing the document. Cancelling that confirmation keeps the owning map tab or application open.
  - Complete documents can be opened and saved as formatted JSON or copied to and replaced from clipboard JSON through one shared validation pipeline.
  - Persisted JSON uses explicit stable property names and format version 2. The shared file/clipboard import upgrades version 1 before binding, preserving its recorded entity masks and initializing missing exact-node masks; newer unsupported versions are rejected before replacement.
  - Visibility snapshots retain exact scene nodes, including non-entity geometry and entity render hierarchies. Hidden overrides are subtracted from an active isolation mask. Optional scene keys distinguish loaded skybox scenes by world group, map, and placement; legacy skybox records resolve only when a single scene matches. Exact nodes resolve only in the recorded map and scene using validated type, name, layer, local bounds, and transform signatures; changed or ambiguous nodes produce notices instead of unrelated matches.
- Main integration points: `GUI/Forms/GameplayFlowForm.cs`, `GUI/MainForm.GameplayFlow.cs`, `GUI/Types/GameplayFlow/`, `GUI/Types/GLViewers/GLWorldViewer.cs`, `GUI/Utils/KeybindingRegistry.cs`, `Renderer/Renderer/Scene.cs`, and `Renderer/Renderer/ViewerVisibilityState.cs`.
- Invariants: node UUIDs provide identity while array order alone determines numbering; group nesting only organizes the timeline and cannot form cycles; empty groups remain visible and manageable; deleting a group promotes its direct nodes and child groups to its parent; `hammeruniqueid` is resolved only inside the recorded map and scene; child flows have one owner and cannot recursively reference an ancestor; node graph connections cannot form cycles; annotations remain session-only and never enter loaded-world storage, entity I/O resolution, or entity export; file and clipboard import check and upgrade the format before validating a temporary document for replacement; newer unsupported formats are rejected without binding or replacement; clipboard export does not clear dirty state and clipboard import requires Save As; restoration preserves camera-transition history and does not change World Layers, Collision tree, Opaque Collision, mesh groups, render mode, exposure, or selection-highlight settings; closing the owning viewer removes annotation GL resources before renderer disposal.

## Code Style

Code must be proper, idiomatic C# that fits the surrounding code, not a first draft. Review and simplify it before finishing so it reads as if a human wrote it.

Standard Microsoft C# conventions, plus:

- PascalCase for private fields
- Always `var` for locals
- Modern C#: collection expressions (`[]`), switch expressions, pattern matching, null coalescing, throw expressions, string interpolation, using declarations
- Expression bodies for properties, indexers, and accessors; block bodies for methods and constructors
- No `this.` unless disambiguating
- Prefer early returns
- `MathF` over `(float)Math` casts; use `MathUtils` helpers instead of inline formulas, and add new general-purpose math there
- Format and parse numbers with `CultureInfo.InvariantCulture`, including interpolation (`string.Create(CultureInfo.InvariantCulture, $"...")`), concatenation and `string.Join`, which CA1305 does not catch
- Usings: System first, then alphabetical, no unused ones. `System`, `System.Numerics` and `System.Collections.Generic` are global usings

### Comments and Documentation

- `//` comments only for non-obvious logic, workarounds, and TODOs; explain "why", not "what"
- Plain ASCII only: no em-dashes, curly quotes, ellipsis, or Unicode math symbols
- Never mention where format knowledge came from (other codebases, tools, game internals) in comments or commit messages
- A type that models a Source 2 schema class, enum or entity links it after its summary with `/// <seealso href="https://s2v.app/SchemaExplorer/<game>/<module>/<Name>"><Name></seealso>`. Prefer `cs2`; an entity class links the class its classname creates. This is the only way to name an engine type; check names and modules against `schemas/<game>.json` in the SchemaExplorer repo
- Don't narrate the change, this conversation, or session codenames; no decorative dividers
- Leave existing comments alone if they are clear and correct
- Public APIs in ValveResourceFormat and Renderer require concise XML docs; use `<inheritdoc/>` on overrides that add nothing new

## Before Committing Checklist

Run these once when the work is done, not after every edit. While iterating, build only the project you changed.

1. Run `dotnet build` and fix warnings and notices. CI builds Release, which enables `TreatWarningsAsErrors` and `AnalysisMode=All`, so build with `-c Release` to catch what Debug misses.
2. Run `dotnet format` to fix formatting. On the `custom` branch, never run it solution-wide; follow the scoped formatting rule under Custom Branch Features.
3. Run `dotnet test` to ensure all tests pass
4. Remove any debug code, console logs, and commented code you added
